「API 路由」页负责 llama-server 服务的启动、停止与运行监控（Token 速度、运行时长与服务日志）。服务启动后提供一个 **OpenAI 兼容**的接口，任何支持该协议的客户端都能直连。

## 启动与停止

页面按「单一主操作」组织：服务停止时主按钮是「启动服务」，运行中主按钮变成红色「停止服务」，旁边保留一个重启图标钮。

- **启动服务**：扫描模型目录并按每个模型的参数生成预设，然后启动 llama-server。模型目录为空（找不到任何 GGUF 文件）时会启动失败并提示，请先下载模型；
- **停止服务**：结束 llama-server 进程，释放显存与内存；
- **重启**：修改模型参数或服务配置后，用重启让新设置生效。

顶部状态卡显示运行状态、运行时长徽标和服务地址（默认 `http://127.0.0.1:8080`，点一下即可复制）。下方「可用模型」列出模型目录里识别到的模型。

## 服务参数

点右上角齿轮图标展开参数面板：

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| 端口 | 8080 | 服务监听端口，范围 1024–65535 |
| 最大加载模型数 | 1 | 同时驻留在显存/内存中的模型数量。它也是启动前内存检查按几个模型**合计**算：每个驻留模型都要留自己的权重 + 上下文缓存 + 运行开销，实测这几个数是叠加的（见下一行） |
| RAM 缓存 MB | 8192 | 系统内存中预留的 prompt 缓存大小；填 0 表示不传 `--cache-ram`，交给服务端默认。**两种服务模式下这个值都只会往下收**：缓存是随对话一轮轮增长的，而启动前的内存检查只算得到开始的那一刻。实测每个不同的 prompt 会按 KV 每 token 体积驻留在内存里（1,035 token ≈ 113 MiB）；按桌面默认值 8192 连续跑 6 个约 6,890 token 的不同请求，进程 RSS 每个再涨约 756 MiB，中途不封顶——十来个普通请求就吃掉那 8 GiB。于是预算取「本机剩余可用内存的一半」：安卓按即将加载的那个模型算，桌面路由模式按「最大加载模型数」能同时驻留的那几个模型**合计**算——取库里最重的 N 条之和（默认 N=1，那就等于最重的一个）。实测 b11720 / 24 GB M2、`--models-max 2`、依次请求四个模型后所有 llama-server 进程的 RSS 之和走 109 → 3,211（big）→ 3,663（big + small-a）→ 1,013（small-a + small-b，big 被挤出）→ 1,010 MiB：一个模型一个 worker 进程，两条加载真的同时在内存里，下一条请求才按 LRU 挤掉一个；只看最重的那一条，等于在你把「最大加载模型数」调到 1 以上之后少报一整条加载。这条预算按每个模型写进预设条目的上下文计价（没调优过的模型现在也会拿到一个明确写进去的上下文：本机当前余量放得下就按它训练时的上下文（最高不超过调优器的 131072 上限），放不下就按调优器的档位往下取。以前这个值是省略掉的，服务端就自己挑一个你控制不了的——实测 4B 的 Q4_K_M 拿到 103,936 token，进程 RSS 冲到 17.0 GiB、swap 从 3.86 涨到 6.30 GiB，而写死 16,384 之后同一模型只要 4.83 GiB；预算又按能同时驻留的那几条加载计价，所以一条付不起的条目就能把整个库的缓存压成 0）。少缓存的代价只是提示词重新处理一遍，比进程被查杀或整台机器开始换页便宜得多。**Mac 上的「剩余可用」按可回收口径取数**（未分配 + 文件缓存 − 已用 swap），与活动监视器一致，不再把文件缓存当成占用而误判成零头 |

服务运行中参数面板会被锁定（显示「服务运行中无法修改，停止后编辑」），避免运行时改配置导致不一致。

## 监控指标

- **生成速度**：状态卡内嵌近 60 秒生成速度的渐变面积图（decode，模型吐字的速度，每秒刷新），思考与回答都属于解码过程；运行中还会同时显示提示词处理速度（prefill，处理你输入内容的速度）；
- **服务日志**：页面下方的日志面板实时显示 llama-server 的原始输出，排查问题的第一现场。应用自己的判断也会写进去两行：`[INFO] prompt cache budget …` 是本机余量把 RAM 缓存预算收小到了多少；`[WARN] 模型 X 这次要占约 …` 是驻留得起来的加载超出了当前空闲内存（「最大加载模型数」为 1 时就是模型库里最重的一次加载）——桌面是惰性加载、多模型共用一个服务，不会因为一条设置就拒绝启动，所以只报一行：点名模型、要占多少、当前只剩多少，服务照常起；「最大加载模型数」调到 1 以上时，报的是**最多 N 个模型同时驻留的合计占用**，并点名其中最重的一个和它自己那一份（合计放不下不一定是某一个模型太大，把那个数字调小也是办法）；能救得回来时还顺带点名**放得下的那一档上下文大小**（按拒绝这条加载的同一套计价算的，含你选的 KV 缓存类型，并且先把同时驻留的其他模型从内存里扣掉），照着填就行。但真去加载它时机器会开始换页，表现为请求长时间没有响应而日志里没有任何报错（实测 24 GB 的 M2 上进程 15.85 GB、swap 越过 7 GB、一个字都没打印）。看到这一行就去「模型设置」照那一档调小上下文，或按一键调优重新规划。独立显存的机器上不报：那种情况下这个数是多计的。Mac 还有**第二道更紧的上限**：GPU 的工作集。Metal 能钉住的量可能比空闲内存还少（实测 24GB M2 报 18186 MiB，而内存刚空出来时 RAM 预算是 18360 MiB），越过它不是开始换页，而是**静默卡死**——加载不报错、健康检查也过，之后每个请求都只回 `Compute error`，不重载模型就不会恢复。这种行报的是工作集上限而不是空闲内存，并把这条后果写清楚；把 GPU 层数设成 0（完全不碰 Metal）的模型库不会被它提醒，因为那种加载根本不需要工作集。

## 用代码调用服务

服务完全兼容 OpenAI Chat Completions 协议，例如用 curl：

```bash
curl http://127.0.0.1:8080/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d "{
    \"model\": \"模型名\",
    \"messages\": [
      { \"role\": \"user\", \"content\": \"你好，介绍一下你自己\" }
    ]
  }"
```

第三方客户端（如各类聊天前端、IDE 插件）中把 API Base URL 填成 `http://127.0.0.1:8080/v1`、API Key 随意填即可（未设置认证时）。

## 局域网访问与 API Key

这两项在「设置」页配置，修改后在下一次启动服务时生效：

- **服务访问范围**：`本地（127.0.0.1）` 只有本机能访问；`局域网（0.0.0.0）` 允许同一网络里的其他设备访问，此时服务地址用本机的局域网 IP；
- **API Key**：设置后，调用推理接口必须携带该 Bearer Token：

```bash
curl http://127.0.0.1:8080/v1/chat/completions \
  -H "Authorization: Bearer 你的APIKey" \
  -H "Content-Type: application/json" \
  -d "{ \"messages\": [ { \"role\": \"user\", \"content\": \"你好\" } ] }"
```

把服务开放到局域网时，强烈建议同时设置 API Key。
